1. Current Status

Live and deployed at supply-rush.onrender.com — commit 711b128
Database: Neon Postgres (external, connected via DATABASE_URL)
Hosting: Render free tier — spins down after ~15 min idle, deploys must be triggered manually (no auto-deploy on push)
Student email verification is currently enabled on the live deploy (left on from testing) — see §6 before running a real class

2. Architecture

A single FastAPI backend serves two plain HTML/JS single-page frontends (no build step, no framework) plus a JSON API under /api.

LayerWhat
BackendFastAPI (Python), SQLAlchemy ORM, served by Gunicorn + Uvicorn workers in production
DatabasePostgres in production (Neon), SQLite fallback for local dev — same code path either way
Student frontendstatic/game.html — one file, vanilla JS, no framework, no build step
Instructor frontendprivate/instructor_dashboard.html — same style, served outside the public /static mount
HostingRender (Docker web service), free tier
Email (student verification)Brevo API (see SETUP_GUIDE.html §5 for why Brevo specifically)

Both frontends follow the same pattern: the page itself is publicly fetchable (no data in the markup), and every actual data operation goes through an authenticated API call gated by a signed cookie — instructor sessions and student verification sessions are two completely independent cookies/mechanisms.

4. Recent Work (This Session)

Chronological, most recent first. Every item below is deployed live.

  1. Instructor login overhaul, team play removed, per-email identity (711b128) — Replaced HTTP Basic Auth (browser silently caches it, so the dashboard never actually re-prompted) with a real login form backed by a browser-session-only cookie. Removed the team/group-name play mechanic entirely; a scenario-code join now resumes the student's own play, keyed by their verified email. The student screen shows "Signed in as X" with a switch-identity link — needed because multiple students commonly share one classroom computer.
  2. Landing screen restructure (fc22640) — New Student/Instructor split landing page. Email verification (when required) now happens before a play is created, not reactively after a 401 — so the play is tied to the email from the start. Added Play.email column.
  3. Email provider migration (34c28d3, 5a48ca8) — Discovered Resend's sandbox mode can't reach arbitrary student inboxes, and SendGrid's signup rejected the account. Landed on Brevo (see SETUP_GUIDE.html §5). Also hit and resolved a Brevo IP-allowlist rejection.
  4. Disruption popup + per-quarter pinning (e180613) — A toast now pops up (auto-dismiss 4s) whenever a quarter with a fired disruption starts. Instructors can now pin a specific disaster to a specific quarter at a specific severity, bypassing that event's random roll for that quarter only.
Prior to this session: instructor dashboard auth, student email verification (original Resend-only version), random disruption events, and outsourcing were already built (bffa30b and earlier).

5. Credentials & Secrets

No credentials are stored in this repo or these docs — everything lives in Render's environment variables for the live service. To find or rotate anything:

WhatWhere
Database connectionRender → supply-rush → Environment → DATABASE_URL (points at the Neon project)
Instructor loginRender → Environment → INSTRUCTOR_USERNAMES / INSTRUCTOR_PASSWORDS
Email sendingRender → Environment → BREVO_API_KEY, plus the Brevo account itself (brevo.com) for sender/IP management
Session signingAuto-generated and DB-persisted if SESSION_SECRET is unset — no manual management needed
If INSTRUCTOR_USERNAMES/PASSWORDS are ever left unset in production, the app falls back to admin + a random password that's only visible in the Render logs (search for [DEV — INSTRUCTOR_USERNAMES/PASSWORDS not set]). Set real credentials before any real class uses this.

6. Known Limitations / Tech Debt

  • Free-tier hosting — Render's free web service spins down on idle (30–50s cold start) and requires a manual "Deploy latest commit" click after every push; there's no CI/CD auto-deploy configured.
  • Brevo IP allowlist — if Render's outbound IP ever changes (not guaranteed static on the free tier), email sending will start failing with a 401 until the new IP is re-authorized in Brevo's dashboard.
  • Student verification is currently ON in production — left enabled from testing this session, domain-restricted to illinois.edu. Turn off or reconfigure before general use if that's not intended.
  • MAX_GROUP_SIZE / PlayMember table — now vestigial. Team/group play was removed; every play has exactly one member (its owner) going forward. The table and env var are left in place rather than torn out, in case group play is reintroduced later.
  • No automated test suite — verification for this session's changes was done via manual local server runs and live browser testing, not unit/integration tests. Worth adding pytest coverage for game_logic.py's simulation logic especially.
  • Old group-based Play rows — any plays created before the team-removal change keep their group_name, but re-joining that scenario code post-change no longer resumes them (a fresh individual play is created instead). Historic data isn't broken, just no longer the "current" play for those old groups.

7. Suggested Next Steps

  • Decide whether student verification should stay on for the live deploy, and if so, set ALLOWED_STUDENT_EMAIL_DOMAIN to the real school domain(s) intended.
  • Consider a paid Render instance (or another host) if cold-starts become disruptive during real class use.
  • Verify a real domain with Brevo (or another provider) for higher send volume / more reliable deliverability than the current single-sender setup.
  • Add basic automated tests around quarter simulation and disruption rolls before making further changes to game_logic.py.
