1. Prerequisites

  • Python 3.11+
  • git
  • A GitHub account with push access to the repo (for deploying)
  • A Render.com account (current hosting) — or any host that can run a Docker container / Python web service

2. Run It Locally

1
Clone and enter the repo 
git clone https://github.com/omkarchougule19/supply-rush.git
cd supply-rush
2
Install dependencies (a virtualenv is recommended but not required) 
pip install -r requirements.txt
3
Copy the env template and adjust anything you need (everything has a safe local-dev default — you can skip this for a first run) 
cp .env.example .env
4
Run the server 
uvicorn main:app --reload --port 8000

Then open http://127.0.0.1:8000/ for the student game, or http://127.0.0.1:8000/instructor for the dashboard.

With no env vars set, the app quietly uses sensible defaults: a local SQLite file (supply_rush.db), no student verification required, and an instructor login of admin / a random password that's printed once to the server console the first time you hit /instructor — search the log for a line starting [DEV — INSTRUCTOR_USERNAMES/PASSWORDS not set].

4. Database

Defaults to a local SQLite file with zero setup. For a real deployment, use Postgres — the current live deployment uses Neon (free tier, serverless Postgres):

  1. Create a Neon project (or any Postgres host — RDS, Supabase, Render's own Postgres add-on, etc.)
  2. Copy its connection string
  3. Set DATABASE_URL=postgresql://... in your environment

The app runs its own migrations automatically on startup (self-healing — it checks for missing columns/indexes and adds them, safe to run every boot). No separate migration command needed.

5. Student Email Verification (Optional)

Skip this whole section if REQUIRE_STUDENT_VERIFICATION stays false — nothing else in this section matters.

If you do turn it on, you need a real email-sending provider. We tried all three supported ones and landed on a clear recommendation:

ProviderVerdict
Brevo ✅ recommendedSignup is lenient, single-sender verification is just a confirmation-link click (no domain/DNS needed), and — critically — no sandbox recipient restriction. Can email any real inbox immediately.
SendGridSame single-sender idea as Brevo, but its signup fraud screening rejected our account outright. Your mileage may vary.
ResendSimplest API, but sandbox mode can only email the address your own Resend account is registered under — useless for reaching real students until you verify a domain you own.

Setting up Brevo

1
Sign up at brevo.com.
2
Settings → Senders, domains, IPs → verify a single sender address (the confirmation email arrives fast — click the link).
3
Settings → SMTP & API → API Keys → generate one.
4
Set BREVO_API_KEY and EMAIL_FROM (the address you just verified) in your environment.
Gotcha we actually hit: Brevo has an IP allowlist security feature on by default. The very first send from a new server IP gets rejected with 401 unrecognised IP address. Fix: Settings → Security → Authorized IPs → find it under the "Unauthorized IP addresses" tab and click the checkmark to authorize it. This has to be repeated if your host's outbound IP changes (e.g. Render doesn't guarantee a static IP on the free tier).

Without any of the three keys set, verification codes are simply logged to the server console instead of emailed — handy for local testing of the flow without any provider configured at all.

6. Instructor Login

The dashboard uses a real login form backed by a browser-session-only cookie — not HTTP Basic Auth. This is deliberate: Basic Auth credentials get silently cached by the browser for the rest of that browser session, so a shared classroom computer would stay "logged in" for whoever opens the dashboard next. The session cookie here has no persistence beyond closing the browser, and there's a working Log Out button.

Set real credentials for production:

INSTRUCTOR_USERNAMES=admin,prof_smith
INSTRUCTOR_PASSWORDS=a-real-password,another-real-password

7. Deploying to Render

The repo ships a Dockerfile, so any Docker-friendly host works. For Render specifically:

1
New → Web Service → connect the GitHub repo.
2
Runtime: Docker (it will pick up the repo's Dockerfile automatically).
3
Add the environment variables from §3 under Environment. At minimum for a real class: DATABASE_URL, INSTRUCTOR_USERNAMES/PASSWORDS, and (if using verification) REQUIRE_STUDENT_VERIFICATION, ALLOWED_STUDENT_EMAIL_DOMAIN, BREVO_API_KEY, EMAIL_FROM.
4
Deploy. Render's free tier only deploys on an explicit trigger (Manual Deploy → Deploy latest commit) — pushing to GitHub alone does not auto-deploy on this plan.
Render's free web service tier spins down after ~15 minutes of inactivity — the next request pays a 30–50s cold-start penalty. Fine for a demo/class; upgrade to a paid instance if that's a problem.

8. Verifying a Deploy

Two endpoints answer instantly and tell you exactly what's configured, without needing to click through any UI:

curl https://your-domain/api/auth/me
# {"email": null, "verification_required": true/false}

curl https://your-domain/api/auth/instructor-me
# {"username": null}   ← confirms the instructor login endpoint is alive

9. Troubleshooting — Real Issues We Hit

SymptomCause & Fix
Could not send verification emailEMAIL_FROM is set to an address your provider doesn't actually let you send from (e.g. a student's own address instead of your verified sender). Fix EMAIL_FROM.
Resend: You can only send testing emails to your own email addressResend sandbox limitation — switch to Brevo (§5), or verify a domain you own with Resend.
Brevo: 401 unrecognised IP addressAuthorize the server's IP in Brevo → Security → Authorized IPs (see the callout in §5).
Render Manual Deploy fails with "Service Unavailable"Check status.render.com — this was a genuine platform-wide outage on Render's end when we hit it, not a config problem. Just wait it out.
Instructor dashboard shows "unauthorized" errors on every actionThe session cookie expired or was never set — log out and back in via /instructor.
